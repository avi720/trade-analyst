# supabase/ — deployed by the Supabase GitHub integration

The schema-change workflow and checklist live in the `db-schema` skill — load it for any
migration. This file covers what matters when touching files in this directory.

## What a push does

Both Supabase projects watch this directory (working directory `.`):

| Push to | Applies to |
|---|---|
| `dev` | dev project `sssichkbdqariguvqprc` |
| `main` | production `nwvswntqrqqtwzrhzpmi` |

The GitHub check is named **"Supabase Preview"** for both; its details link names the project.
On a PR it shows **"skipping"** — Automatic branching is off, so there is no preview database to
test against. The `dev` push is therefore the only rehearsal: a migration goes to `main` only
after its check on the `dev` push is green.

## migrations/

- Filename `<yyyymmddHHMMSS>_<snake_name>.sql`, **UTC**, later than the newest file. The
  filename is the version recorded in both databases.
- **Never edit a pushed file.** The integration only applies new versions, so the edit never runs
  and the file silently diverges from both databases. Fix forward with a new migration.
- **Never delete a pushed file on its own.** The database still records the version, and the
  next deploy fails on "remote migration versions not found in local migrations directory".
  For a migration that ran **only on dev** (a test, a mistake caught before `main`): on the dev
  project undo its objects and `delete from supabase_migrations.schema_migrations where version
  = '<version>'`, then delete the file and push. Done once on 2026-10-11 for
  `integration_smoke_test`. Once a migration has reached production, fix forward instead.
- The 49 files up to `20261011065622_add_broker_connection_token_expiry_tracking.sql` were
  exported byte-for-byte from production's `schema_migrations.statements` (md5-verified) when
  the integration was set up. They are the record of what ran — don't reformat them.

## config.toml

- Generated by `supabase init` (CLI 2.120.0). Almost all of it is local-dev settings, which the
  integration ignores — **except Edge Functions and Storage buckets declared here, which are
  deployed to production on merge to `main`.** None are declared today; adding one is a
  production change, not a local tweak.
- Edge Functions under `supabase/functions/` are Deno TypeScript, and the root
  `tsconfig.json` includes `**/*.ts`, so `npm run build` would type-check them and fail. Add
  `"supabase"` to `exclude` in `tsconfig.json` before adding the first one.
- `.temp/` and `.branches/` are CLI state, ignored by `supabase/.gitignore`.
